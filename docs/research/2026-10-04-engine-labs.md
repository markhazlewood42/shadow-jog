# Engine design lab record (2026-10-04)

This page keeps the evidence behind the engine design docs in `docs/engine/`. Six research agents read the code and the libraries, and some of them ran small labs (headless Chromium on SwiftShader, device pixel ratio 1 unless a line says otherwise). Each research leg then had an independent fact-checker.

How to read it:

- **Findings** are the load-bearing claims of each leg, as the research agent wrote them.
- **Fact-check** lists every claim the checker corrected, refuted or could not verify. A claim not listed there was confirmed or not checked.
- Lab code paths point to `media/research-2026-10-04/design-labs/` and `media/research-2026-10-04/benches/`. That folder is git-ignored and exists on Mark's machine only. Paths marked "session scratch, not kept" were not saved.
- Nothing here ran on a real GPU in CI, in Firefox or in Safari. The Phase 0 lab in `docs/engine/migration.md` re-runs the claims that matter.

## PixiJS v8 under our engine

Pixi 8.22.0 (npm latest, published 2026-10-01) can be the renderer under the Shadow Jog engine. I checked each API claim against the installed package source and types, then ran about 20 headless Chromium (SwiftShader) experiments and several bundle builds. Use a bare WebGLRenderer, not Application. Our fixed-step loop calls renderer.render({ container, clear: false }) once per frame. The engine creates one WebGL2 context (stencil on, antialias off) and passes it to both Pixi and Three together with its canvas. The pixel-art path works: nearest as the default texture style, roundPixels, resolution 1 at 480x270, canvas textures refreshed with source.update() (a full 480x270 Canvas 2D frame came out pixel-exact), per-object filters exact at resolution 1, and a RenderTexture upscaled by a whole number (x3, x4) exact. Per-object filters, custom GLSL filters, stencil and sprite masks, fixed-function blend modes and the community bloom, shockwave and CRT filters all ran on the shared context with Three and 0 GL errors, so the "special effects" requirement is feasible. That holds only after three traps are handled. Pixi's resetState keeps a stale GL clear colour, so filters and sprite masks paint over the 3D picture (fix: gl.clearColor(0,0,0,0) after Three renders). The official guide's init snippet omits the canvas, so Pixi never recovers from context loss. Three's default context has no stencil, so Graphics masks silently fail. Other hard limits: advanced blend modes (overlay and similar) cannot blend against Three pixels, renderer.destroy() kills the shared context, and a new Three renderer per 3D entry leaks GL objects, so create each renderer once and tear down only scenes. Bundle cost is about 151 kB gzip for the bare renderer, 195-205 kB for the useful subset, plus 50-66 kB for pixi.js/text-bitmap, so the 236 kB alarm must be re-set; our own canvas-drawn font can feed BitmapText through a hand-built BitmapFont if lineHeight equals fontSize. The Canvas renderer exists but skips every filter and draws no meshes, WebGPU is experimental and untested, the package's own docs and bundled agent skills are partly wrong (Filter.from with only a fragment shader throws), a top-level await on init hangs silently in a Vite build, and the default build lets Tab open Pixi's accessibility overlay while the game maps Tab to the menu. Everything was measured on Chromium with software GL at device pixel ratio 1 (events also at 1.25), so real GPU, Firefox, Safari, WebGPU and parity with the Phaser stage are unproven. **Added by the fact-checker:**

- Pixi's shared Ticker auto-starts its own requestAnimationFrame loop the first time anything adds a listener to Ticker.shared (AnimatedSprite, GifSprite, VideoSource, CanvasObserver), even with a bare WebGLRenderer and no Application. That is a second, wall-clock-driven timing source beside the fixed 60 Hz simulation. The engine must set Ticker.shared.autoStart=false and stop() it, then drive it from its own loop (Ticker.shared.update(time)) or never use those classes. Prepare also uses Ticker.system.
- The GL clear-colour hand-off fix is order-sensitive for the patch variant and fragile for any other raw GL (the GL presenter, a future Three post pass). Because filter and mask render targets clear to [0,0,0,0] and Pixi trusts its own cache, any engine code that changes gl.clearColor without calling the hand-off module will re-break filters. Safest design: one module owns every transition between Three, Pixi and raw GL, and a Playwright pixel test (the e16 gap pixel) runs in CI and on every Pixi upgrade. I reproduced the failure and both fixes myself in e16.
- Pixi's GCSystem runs after every render and unloads GPU resources unused for 60 s (gcMaxUnusedTime 6e4, default on). Scenes or UI not drawn for a minute (a menu, a battle stage during a long 3D hack) will re-upload or rebuild on return, causing a first-frame hitch. The engine should either set a longer gcMaxUnusedTime or gcActive:false for the small fixed 480x270 asset set, or call prepare before showing a scene. The researcher noted the canvas-source rule but not the Graphics geometry and ImageSource texture GC.
- pixi-filters is stale relative to Pixi (last release 2025-11-29, 10 months and about eight Pixi minors ago) and is the planned source for bloom/shockwave/CRT. The architecture should treat community filters as vendored or copyable GLSL behind the engine's own Effect interface, not as a dependency every effect imports directly, so a Pixi minor that breaks one filter does not block the engine upgrade.
- Custom filters must be written with both a vertex and a fragment GLSL source because the bundled skill examples (Filter.from with fragment only) throw. The engine's Effect/Filter authoring template and any agent-facing docs must include the vertex shader (Pixi's default filter vertex) explicitly, and a Node-level smoke test cannot catch this without a DOM stub.

## Three.js 3D view inside Pixi

Recommend approach (b): the engine creates one WebGL2 canvas and context, Pixi v8 renders on it, and Three.js is imported lazily on the first entry. Three renders at 480x270 into a NearestFilter WebGLRenderTarget, and Pixi samples that texture through the public ExternalSource class (added in Pixi 8.16.0, still marked advanced). The result inside the Pixi back buffer is pixel-exact against a CPU reference on SwiftShader, an RTX 4070 and Firefox, including a per-object filter on the 3D sprite, a root filter, a Graphics mask on the 3D sprite and an integer x3 nearest present. The fallback is (c): Three on its own canvas, copied into Pixi through CanvasSource. It is also pixel-exact and has no shared-state hazards, but it costs about 0.9 ms more per frame on SwiftShader and about 2 ms more in Firefox, and it needs an explicit forceContextLoss per entry or Chrome evicts Pixi's context. The guide's approach (a), Three drawing to the default framebuffer under Pixi, cannot filter the 3D frame at all (a root filter left 717,792 of 717,792 3D pixels unchanged), and (d), a stacked canvas, was only reasoned about, not benchmarked. Testing found three traps that the Pixi guide does not mention. Pixi 8.22 resetState() clears its clear-colour cache without calling gl.clearColor, so Three's background colour leaks into Pixi filter and render-texture clears (fix: call three.resetState() after Three renders too). The guide's init omits the canvas option, so nobody calls preventDefault on the real canvas and the context can never be restored. And renderer.destroy() on a shared context loses the context for good, so Pixi is created once and never destroyed. Lifecycle is clean if Three is created once and each entry creates only a render target, scene, glTF and ExternalSource: GL object counts stayed flat over 30 cycles on the RTX 4070, 10 on SwiftShader and 10 in Firefox. A new Three renderer per entry leaks 5 textures and 3 framebuffers, and EffectComposer.dispose() leaks 11 textures and 11 framebuffers per cycle unless each pass is disposed. A lost context raises webglcontextlost within about 2 ms and neither library throws, so a story script's 3D promise can resolve with an aborted or unsupported result immediately. A restored context needs the ExternalSource re-wrapped (125,088 wrong pixels if it is not) or the session ended. Exact palette colours need ColorManagement.enabled=false and no OutputPass when rendering to a render target. Costs at 480x270 with 300 meshes, fog and bloom on SwiftShader: b 3.1 ms, b with Pixi bloom 5.7 ms, b with UnrealBloomPass 7.8 ms, c 3.5 ms. On the RTX 4070 every variant is about 0.4 ms. The SwiftShader near-plane trap reproduced (long lines lost about 21% of their pixels) and is fixed by segments of 10 units or less. Safari, mobile, a Linux CI runner and Mark's look review are not covered.

## Tooling, testing and CI

The Shadow Jog engine can be tested in four tiers: Node unit tests, Playwright on SwiftShader, local GPU runs, and a bundle gate built on the Vite manifest. In plain Node 24, Pixi 8.22 can build and measure a scene graph (Container, Sprite, Graphics, masks, render groups), and Three r186 can run its whole scene logic. Only the renderers, Text, AnimatedSprite and custom Filter shaders need a DOM or a GPU, so the engine must keep those behind one render seam. Playwright 1.63 adds the SwiftShader flag by itself, and its headless Chromium gives WebGL 2. Today's GL presenter is never tested on CI, because the repo skips it by renderer name. With Pixi the whole game runs on software GL in CI, so effects need a runtime tier (full, lite, none), and the e2e viewport must stay at 960x540. My measurements show that filters must run at game resolution: a 480x270 render texture, then a nearest-neighbour upscale. This keeps every game pixel an exact block at DPR 1 and 1.25, and a filter at the upscaled size breaks it. The same frames are bit-identical on a real GPU and on SwiftShader when nothing is filtered. Filtered frames differ by at most 3/255, so the rule is exact goldens without filters and a small tolerance with them. The JS timer in perf.spec cannot see GPU cost, so CI needs a frame-interval gate, patched-GL draw-call counts and GL-object leak counts. Vite 8.3.1 can pull a 130 kB Pixi chunk into the boot entry when a named chunk group is used, so the budget needs a manifest-based gate with classes (boot, lazy-2d, lazy-3d, other). **Added by the fact-checker:**

- The Chromium used for every measurement (rev 1234 / Chromium 151) is not the one Playwright 1.63 will install on CI (rev 1243 / Chromium 153.0.8010.12). SwiftShader frame costs, pixel-exactness, GPU-vs-software diff, and context-loss behavior are all unverified on the CI browser. Any golden or threshold must be re-derived from the first CI run (or from the exact binary `npx playwright install` fetches locally).
- Renderer fallback is a deliberate engine choice, not an accident: autoDetectRenderer with a string preference appends the other renderer types (webgl, then webgpu, then canvas), whereas an array preference is exclusive and throws if nothing matches. The engine should pass an explicit array. That lets it keep today's Canvas 2D path (or its own no-effects tier) as the no-WebGL fallback during the incremental migration, instead of getting Pixi's CanvasRenderer, which silently drops every filter and mask-less effect, plus an extra lazy chunk.
- The recommended 'filters at game resolution' architecture (stage -> 480x270 RenderTexture -> nearest upscale) costs more than the headline numbers: with the blur+cm+shock stack on SwiftShader it measured 12.6 ms mean / 13.6 p95 at 960x540 and about 20 ms at 1920x1080, versus 10.2 / 11.5 and 18.1 for resolution=k. The extra full-screen blit and RT pass is paid every frame. Budget the full effects tier accordingly, and the 'lite' tier should drop the whole-scene filter stack in favour of per-object filters or a single pass.
- Pixi's default GC unloads image-backed texture sources unused for 60 s (ImageSource sets autoGarbageCollect = true) and re-uploads them on next use; RenderTexture/TextureSource defaults are autoGarbageCollect false, so baked render textures are not collected by GC, but they are still lost on context loss. The engine's baked-texture registry therefore only needs to handle context loss, not GC. Tests that watch GL texture counts across 3D hack mode (Pixi scenes idle for a long stretch) must account for ImageSource textures being unloaded and re-uploaded.

## The Phaser spike and the benches

The Phaser spike is a thin layer over Phaser. Only 9 of its 57 TypeScript files in src/stage and src/stage/edit import phaser. About 3,378 lines in 8 files (boot, hud, hudkit, labhook, livefx, stagescene, stills, textures) call renderer APIs. A further 2,813 lines depend only on the StageScene or Fighter shape, and about 8,047 of the 15,303 lines use neither. The runtime Phaser surface is about 15 display-object methods plus 6 TextureManager methods. The spike used Phaser only as a display list and a renderer, with its own fixed 60 Hz tick driving everything, so the Pixi engine needs very little from the renderer. The Battle Stage Editor never touches a Phaser object. It reads about 10 plain Fighter fields and calls about 12 StageScene methods, so it ports with the scene API and not the renderer. The parity bench (d2d.ts plus phaser-shim.ts, about 450 lines) ran the unchanged spike stage on a Canvas 2D display list, which proves the seam is narrow. It did not measure Pixi, filters, masks, real art or editor dragging. The exact Phaser-to-Pixi v8 mapping is in the findings. Four items need design decisions. Pixi has no camera, so the engine needs separate world and HUD layers. Pixi has no flipX, and Phaser flips about the texture middle, so mirrored enemies need a rule. Pixi has no texture bag, so the engine needs its own TextureStore. Pixi has no pixel-alpha lookup, so picking should use CPU-side pixel data. The shared-context glue (Three renders first, then Pixi, with resetState on both) is about 15 lines and was pixel-exact for 600 frames. It was tested with Three creating the context, which is the reverse of what a lazy 3D chunk would do. Never destroy the Pixi renderer on a shared context, and note that Pixi's Canvas fallback skips shader filters. **Added by the fact-checker:**

- The existing GL presenter (bloom, shockwaves, the 'real differentiator' effects home) is refused on SwiftShader by name (SOFTWARE_GL regex in GlPresenter.create), so CI never runs it. Any Pixi filter/effects layer that replaces it will likewise have no automated pixel test unless the design adds an explicit CI path (a SwiftShader allow-flag, a CPU reference, or a GPU runner). Bench-patched presenter cost about +23 ms/frame on SwiftShader.
- Pixi's Canvas renderer differs structurally from its WebGL renderer, and cannot be assumed a faithful fallback: Phaser's own Canvas vs WebGL showed 1.9% pixels differing with max channel diff 124; in Pixi, custom shader filters are skipped, unsupported blend modes degrade to source-over, and CanvasFilterSystem only covers CSS-filter-capable filters. The design must decide whether a no-WebGL path exists at all for the Pixi scenes (a 'degraded mode' contract), or whether the existing Canvas 2D engine remains the fallback during and after migration.
- Context-attribute requirements are part of the 3D/2D integration contract: the bench created the context via Three with stencil:true because Pixi masks need a stencil buffer, depth:true for Three, alpha:false, antialias:false. A lazy 3D chunk that attaches to a Pixi-created context needs the Pixi context created with stencil and depth up front (attributes cannot be added later), which is untested. Alternatively the offscreen-canvas-as-texture approach removes the constraint.
- The spike's frame callback is Phaser's update(time, delta) plus PRE_STEP/POST_RENDER events for frame timing, and the shim emulated them. A Pixi engine must choose bare renderer vs Application: Application attaches a shared Ticker that auto-starts and renders on its own rAF, which would conflict with the single fixed-step loop owning render timing and with the game.run() scene stack. The design should state that Ticker.shared/Application are not used (render called explicitly after the sim step) and where per-frame stats hook in.
- Texture identity is string-keyed throughout the spike and its e2e specs: f.shown = `${texture.key}/${frame}` is used to skip redundant setTexture, e2e reads sprite.texture.key, and variants (tint-, haze-, flash-, mirror chips) derive keys from base keys with copied frame names. A Pixi TextureStore must preserve stable string keys and per-key frame tables (Texture has only a debug 'label'), or the change-detection, pruning-by-prefix and tests all need rewriting.

## The current engine

The current engine is a small immediate-mode core: 2,894 lines in src/engine across 16 files, inside a 36,822-line TypeScript game of 130 files. It has no runtime dependencies. A fixed 60 Hz loop (up to 5 catch-up ticks per animation frame) feeds a scene stack. Each Scene has update() and render(ctx: CanvasRenderingContext2D), and game.run(scene) returns a Promise that resolves when the scene closes. Story scripts depend on that Promise contract: chapter1.ts has 281 `await s.` calls and the map files 106 more. A new engine must keep game.run, the Scene lifecycle and the whole ScriptApi surface (script.ts:18-87), and a 3D mode can enter through the same door as the shop or a battle. The 480x270 size lives in one export (game.ts:21-22) imported by 34 files, but 240x135 is separately hard-coded in 3 modules plus the FX lab, and 480/270 literals remain in main.ts and fieldmap.ts, so the shared W/H module is more than a re-export. Display scaling is device-pixel aware (display.ts:91-115). The WebGL presenter (presenter.ts) is a complete effects pipeline, and it refuses software renderers, so CI has never executed it. The pipeline is bloom, 4 shockwaves, colour split, 4 hazes, 2 glitches, stage dim, flash, vignette and 4,096 GPU particles, driven by data in fx.json that Mark edits in the FX lab. Roughly 60% of the ~2,100 raw canvas calls are bake-time painters that output canvases (props, backdrops, enemies, buildings), so shared art can enter Pixi as textures unchanged. The code that must be rewritten for retained mode is the per-frame scene, UI, lighting and effect drawing, about 600 raw calls plus ~270 drawText and 57 drawWindow call sites. The battle rules in src/battle (engine, ai, setup, types) are DOM-free and tested in Node. battle/fx.ts is not DOM-free. Audio (WebAudio synth, sequencer on setInterval), saves and settings (localStorage) have no renderer coupling. The e2e suite relies on window.__SJ__, #screen/#fx/#boot DOM ids, scene internals reached by name and monkey-patched tick/update/render, and has no golden-image comparisons. Missing for a real engine: scene graph, camera object, asset cache and loader, tween or timeline, signals, entities, render-to-texture and a resource-disposal lifecycle.

## Engine conventions

Phaser's scene model is the best single base vocabulary. A Scene owns its own display list, cameras, input, loader, clock and tweens, runs init, preload, create and update, and is driven by queued ScenePlugin operations (start, launch, run, pause, resume, sleep, wake, stop). Phaser has no concept for a fixed-step simulation (its main loop uses a smoothed variable delta), an input-action map, audio buses, prefabs or awaitable scenes. Shadow Jog must borrow those from Unity (FixedUpdate, Input System action maps, prefabs, Awaitable, URP Volumes), Godot (_physics_process, InputMap, AudioServer buses, await, y-sort) and Gaffer's accumulator. PixiJS 8.22 is only a renderer: it has Application, Container, RenderLayer, Ticker, Assets, filters and masks, but no scene manager and no camera class. Our Scene, Camera, Input and timing classes are therefore ours, and Pixi can run under a host-owned loop (autoStart false, manual app.render()). Phaser 4 and Pixi agree on per-object "filters" and "mask", which gives the special-effects layer one shared name. Two silent port traps exist: Phaser's default origin is 0.5 but Pixi's default anchor is (0,0), and the whole-pixel rounding settings differ. Four names collide across engines (Scene, run, Layer, Timeline), so the design doc needs a glossary-style table that says which meaning wins. Three.js has no scene manager, input or tweens, its Clock is deprecated in favour of Timer, render() silently returns after a context loss, and GPU resources need explicit dispose(), so the 3D mode should sit inside one of our Scene subclasses with Three names kept unchanged inside it. The recommended vocabulary is in the four VOCAB findings.
